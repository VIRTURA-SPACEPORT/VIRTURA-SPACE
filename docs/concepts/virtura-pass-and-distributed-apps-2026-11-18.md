# VIRTURA ID / Pass 与分布式应用体系：2026 封闭测试路线

> 日期：2026-11-18｜状态：产品与技术规划 v0.1，**不表示已上线功能**  
> 主体：VIRTURA Space（团队平台）｜关联：[VIRTURA VJ BATTLE 概念](./virtura-vj-battle-2026-11-18.md)  
> 当前代码：[VIRTURA-SPACE](../../README.md)

**近期扩充**：VIRTURA VJ Battle 的 SceneForge 线上/线下集会与数字场地对接见 [混合赛事方案](./virtura-vj-battle-sceneforge-hybrid-2026-11-18.md)。身份与 Pass 承担用户及权限，不承担 3D 渲染、物理舞台控制或实时播控。

## 01. 产品边界：一个 ID，多种前台

- **VIRTURA Space**：可浏览的场馆、应用、作品和活动的统一入口；公众内容无需先登录。
- **VIRTURA ID**：唯一主体身份（用户拥有一个平台 UUID），承载收藏、继续体验、本人选择公开的参与记录、个人物品、可撤销权限。
- **VIRTURA Pass**（工作名）：VIRTURA ID 的**参与凭证与界面表现**。不是另一个账户，也不是执业许可、政府身份、NFT、成员证或支付账户。
- **VIRTURA VJ BATTLE / 独立活动 App**：可以有自己的 URL、视觉风格、赛季、赛组、任务与作品，但调用平台统一授权与档案。未来其他活动、展馆、XR 工具可采用相同方式。
- **VIRTURA Collective**：组织、活动主办与对外服务身份；组织正式成员身份与平台测试访问不是一回事。
- **My Space**：一个便于“继续上一件事”的轻量账户界面，而不是第二套操作系统。

应用可以无限扩展，**单个用户会话的下一步只能有限而明确**。应用扩展能力不意味着首页必须显示所有应用。

## 02. 当前可确认实现（2026-11-18）

- 本仓库已发布 [Cloudflare Pages 预览](https://virtura-space-preview.pages.dev/sign-in)，具有邮箱 OTP 登录、`/id` 个人面板、Supabase 同站转发、登录退出流程。
- 现有 `public.virtura_memberships` 仅含 `admin/member` 与 `active/revoked`，当前一个管理员账号；它是成员授权表，**尚不能把所有外部内测者都叫“团队成员”**。
- 另有 `closed_test_applications` 与 `closed_test_email_outbox`（申请记录与发信状态）。申请保存、邮箱回执、批准邀请、实际登录是不同事件。
- 当前尚无数据库级 `saved_items`、`user_passes`、`external_identities` 或赛事业务表；不要在 UI 假装用户已持有收藏、积分、证书或活动记录。
- 唯一技术主线目前为 React/Vite、Cloudflare Pages 和 Supabase Auth/Postgres；网页端身份与平台小程序身份打通需要额外开发，不能认为已有电子邮箱账号就自动支持微信或小红书账号登录。

## 03. 三层用户体验与第一个动作

| 层 | 人第一次进入看到什么 | 当前应提供什么 | 不提供什么 |
| --- | --- | --- | --- |
| Public / 公众 | 一件可打开的真实作品或服务、活动与内测申请 | 查看、试用、阅读、申请 | 假倒计时/假人数/虚构赛程 |
| My Space / 个人 | 最近可继续的项目，有限收藏、明确的授权 | 继续、保存、取消收藏、查看邀请状态 | 空洞的“数字人生”面板 |
| Workspace / 协作 | 一项被授权的小任务，明确交付与负责人 | 接受/拒绝、提交、验收、退出 | 任何注册者都能读取团队工作区 |

首次引导：不超过 3 个步骤；多数内容无需全屏引导；只在用户尝试保存、提交、参加活动时解释登录价值。一次界面只突出一个主操作，可跳过操作提示。

## 04. 外部测试资格与团队成员权限拆开（P0）

现有个人面板中普通 `member` 叫“受邀成员”，下一版要区分：

1. **auth user**：某个邮箱通过 OTP 验证身份，不代表任何业务访问权。
2. **closed test grant**：授予某个用户或应用在某个期间访问特定实验的资格；可过期、撤销。
3. **collective membership**：真实团队身份（admin / member），不依赖是否通过某个比赛。
4. **project assignment**：某项目的具体角色、可访问资源、责任与期限。
5. **participation / evidence**：活动出席、练习、作品与评审证据；这是历史事实而非权限。
6. **pass / credential**：某次参与或能力的展示结果，经授权才能公开，并注明发行人和标准。

建议新增 `beta_access_grants`（user_id, app_id, scope, status, issued_at, expires_at, revoked_at, approved_by），保留 `virtura_memberships` 作为组织成员表。不能仅靠前端隐藏按钮限制访问；内容数据必须在服务端/API 与 RLS 限制。后续再开发管理端，不引入可被普通用户调用的“自助提权”接口。

**P0 验收**：管理员通过服务端批准/撤销测试资格；未获准、撤销、过期者不能读取对应受限资源；现有 admin 仍可登录；账号创建不受公开申请直接触发；发信失败可重试且不重复授权；敏感操作有审计记录；撤权测试覆盖已登录会话与刷新后的会话。必要时用短有效期授权或服务端再次校验，不能仅依赖尚未刷新的 JWT 声明。

## 05. My Space 首个完整功能：收藏（P1，已获方向认可）

用户同意先做 **My Space 收藏**。第一版只实现以下闭环：

1. 游客能打开真实存在且可公开访问的作品/应用详情，无须账号。
2. 用户选择“保存到 My Space”时，清晰要求登录并解释保存后可跨设备找回。
3. 已获准 ID 用户点击一次保存，页面确认成功；连续点击不会产生重复记录。
4. `/id` 页面展示用户自己的收藏，能打开原条目、取消收藏，并有空状态。
5. 未登录、其他用户、已撤销权限者不能查询不属于自己的数据；测试两个不同真实账户的行级隔离。
6. 若原条目下线或变私有，收藏保留引用，但以真实状态显示“暂不可访问”，不可借收藏绕过授权。
7. 支持最终导出/删除自己的保存列表（可以后续版本提供，但数据契约先规划）。

推荐 `saved_items`：`id`、`user_id`、`target_kind`、`target_id`、`created_at`、唯一键(`user_id`, `target_kind`, `target_id`)。`target_kind` 初期只开放已核实的一两类公开对象。避免使用任意 URL 作为可绕过检查的目标；数据 API 用 RLS 限制 `auth.uid()=user_id`，服务器端校验对应目标真实存在与当前权限。

**不要**把收藏、练习成绩、活动纪念、可交易物品和权限全部写入一张 JSON 万能表。每种数据有不同的真实性与授权约束。

## 06. 多端产品组合（先 Web 再各宿主端）

| 载体 | 最适合的微型能力 | 统一身份接入路径 | 首期判断 |
| --- | --- | --- | --- |
| 网页 / PWA | 浏览、收藏、完整 Battle Briefing、作品提交、赛程 | 现有邮箱 OTP / Supabase | **当前主线** |
| 微信小程序 | 活动预约/签到、Pass 卡、赛场二维码、个人收藏摘要、通知 | `wx.login` → 服务端验证 code / openid → 经用户确认绑定 VIRTURA ID | 先研究，等真实活动入口需要时 |
| 小红书小程序 | 展览/赛事体验卡、作品卡片、活动报名与分享后回访 | `xhs.login` → 服务端 `code2Session` / `open_id` → 显式绑定 ID | 受平台准入和审核约束 |
| Mobile Web / 原生壳 | 深链接进入具体实验、通用个人数据 | 手机网页统一登录；以后按需用正规 OAuth/OIDC | 不急于开发原生 App |
| WebXR / Quest / AVP | 交互赛场、空间节点和视听演奏 | 浏览器支持时用安全的网页登录/设备关联；会话短有效期 | 设备/浏览器单独验收 |
| 场馆屏 / 控制室 | 只读赛程、获批准的输入与作品展示 | 经管理员分配的设备凭据与最小权限 | 与个人登录分离，不能把个人访问令牌写进公开屏幕 |

**登录原则**：不是所有终端把 `supabase-js` 和邮箱验证码直接复制过去。小程序通常提供独立的平台登录码。平台服务端应验证平台身份、把经过明确确认的外部身份绑定到已登录 VIRTURA ID，然后给当前端签发最小权限、短生命周期的应用会话。不同端使用相同用户 ID，但每端有自己的可信登录过程；不以昵称、头像、可修改手机号猜测为同一人。

建议的 `external_identities`：`user_id`, `provider`, `provider_subject` (openid/unionid 的可靠作用域), `app_id`, `linked_at`, `verified_at`, `revoked_at`。组合唯一约束按各平台 subject 作用域设计。账号合并和解绑需要双端或邮箱再次验证、审计和防账户劫持设计；未核实微信 UnionID 共享范围前不要跨 App 自动合并 OpenID。

任何密钥（Supabase `service_role`、微信 appsecret、小红书服务端密钥、会话密钥）只保留在服务端；不放进小程序、网页 JS、日志或 GitHub。

### 官方文档要点（2026-11-18 搜索）

- [微信登录对接，腾讯云 OneID](https://cloud.tencent.com/document/product/1441/68677)：`wx.login` 与 openid/unionid 的服务端关联思路；具体小程序功能最终以微信开放平台自身要求及 VIRTURA 应用资质为准。
- [小红书小程序介绍](https://miniapp.xiaohongshu.com/doc/DC137160)：非交易型小程序可提供互动服务；支持多种入口，但小程序需单独开发、主体认证与审核；非交易型不能默认支持支付。
- [小红书小程序登录态](https://miniapp.xiaohongshu.com/doc/DC473950)：`xhs.login`、`code2Session`、`open_id`；临时代码只能用一次，会话密钥不得下发。
- [小红书小程序开放平台](https://miniapp.xiaohongshu.com/)：主体认证、类目、备案、开发和发布审核；站内投放和复访能力不等于“已获运营资质”。
- [小红书开放平台（另一类 OAuth 入口）](https://openaccount.xiaohongshu.com/)：需与小程序内登录能力区别核实，不要误认为不同产品自动共享登录。
- 这些都是潜在对接渠道，**当前均未在 VIRTURA 完成认证、开发与联调**。

## 07. Pass 与“数字物品”的最低限度数据契约

Pass 最初是一张记录 **“参加过什么、保存了什么、完成了什么、下一个活动在哪”** 的非交易参与卡。

建议数据实体：
- `assets` / `releases`：作品、作者、版本、许可、固定链接；
- `activities` / `editions`：活动与版本、明确日期和运营人员；
- `participation_records`：获授权的参加/完成证据；
- `ability_evidence`：技能测试版本、条件、评分和复核，不自动成为职业资格；
- `pass_artifacts`：活动纪念和用户主动公开的内容；
- `quota_usage`：只记录真实受限资源的消耗，不充当货币和信用分。

“收藏”不等于获得作品版权；“出席”不等于通过能力测试；“评级”不等于正式组织成员；“纪念物”不等于可以转售的 NFT。最终支持导出、撤销公开与删除个人数据的路径。

## 08. 每日额度与反成瘾设计

日常阅读和基本体验无硬性次数门槛。只有存在真实成本或稀缺性的资源（例如云 GPU、活动排练工作站、公共素材下载带宽、实时赛场时隙）才设配额：`resource_id`、`scope`、`period`、`limit`、`used`、`refund_reason`、`policy_version`。按用户/团队/活动期划分。用户可以知道剩余、重置时间和规则；技术故障或无障碍例外可由负责人补还。

比赛公平资源和付费权益绝对隔离。不要做让用户为“每天任务额度”不断上线的心理操纵。界面推荐一次专注 5–15 分钟；可跳过、可继续、可退出，长期目标由用户自己选。

## 09. 可复用 App 的登记规范

一个应用注册记录初期只需要：`app_id`、`name`、`owner`、`source_repo`、`launch_url`、`entry_task`、`platforms`、`auth_scope`、`data_permissions`、`maturity_status` (open/limited/experimental/archived)、`license`、`version`、`maintainer`、`support_contact`。

发布前的必要验收：
- 一个实际操作可完成，不只是宣传卡/404/永远加载；
- 数据最小访问权限并可撤销；
- 设备适配、失败回退、已知成本和许可明确；
- 作者及团队责任区分；
- 至少测试一次退出、重新登录、保存与跨设备恢复；
- 同一应用既可在主平台被发现，也可有自己的外部传播入口，链接身份时不暴露用户令牌。

**不要求所有 App 同一 UI 风格**；允许品牌、小游戏、展馆各自表达，但同一用户的隐私控制、登录和返回路径须一致。

## 11. 发布和安全底线

- 新架构先在团队仓库和分支审查；不能未经核实覆盖 `virtura.space` 生产维护页。
- 公众入口清楚区分“已开放 / 受邀测试 / 计划中”；不显示未经验证的资产、排名、奖金、已获得身份。
- 账号与权限不能通过前端控制；所有受限数据后端鉴权。
- 认证信息、IP、参与者作品、评审记录只按明确用途收集；个人资料不出现在公开日志与团队公开仓库。
- 活动的商业授权和用户同意与日常登录条件分开；素材可撤回、争议可复核。
- 2026-12-03—12-04 有既有演出制作优先级；平台扩展不得挤占既定现场交付。
